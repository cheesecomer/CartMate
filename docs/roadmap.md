# ロードマップ

MVP は5つのフェーズに分けて実装します。各フェーズの終わりに動作とコードをレビューしてから、次に進みます。

## フェーズ1: 基盤とローカル状態の UI

- Gradle 構成（`app`, `domain`）、Version Catalog、Hilt、テーマ、Navigation。
- テスト基盤と CI: `domain` と `app` の単体テスト（JUnit、Truth、coroutines-test、Turbine）、Compose UI テスト、GitHub Actions（単体テストと lint）。rules-test と Firestore エミュレータを使う結合テストの基盤はフェーズ2で用意する。
- `domain` のモデルと Repository インターフェースを **最終形で** 定義する（フェーズ2で実装を差し替えるだけで済むように）。
- インメモリ Repository（チェック・Undo は [sync.md](design/sync.md) と同じ意味論。購入履歴の記録も含める）。
- 画面: リスト一覧（作成、未購入件数、空リストの削除）、リスト詳細（追加、数量・単位、チェック、Undo Snackbar、チェック済みを元の位置に打ち消し線で表示、スワイプ操作、項目の編集と削除）。
- 入力状態の reducer と IME フロー（サジェストの中身は空でよい）。
- **完了条件**: エミュレータ上で、ログインなしでリスト作成・連続追加・チェック・Undo・削除ができる。reducer のテストが通る。

## UI の土台（フェーズ1のあと・完了）

以降のフェーズで追加する画面がそろって従うよう、見た目の基準を先に決める。画面ごとの細かい作り込みはしない。配色は次の「デザイン刷新」でライラックに置き換える。

- テーマ: ブランドカラー（グリーン）から作った配色。白を基調にし、端末がダークモードでも白のままにする。端末の壁紙に合わせた配色（Dynamic Color）は使わない。クリーンな印象（広い余白、影の代わりに細い区切り線）にする。
- アプリアイコン: カートとチェックマーク。テーマアイコン（単色表示）にも対応する。
- 共通の部品の基準: 余白、行の高さ、空の状態の表示、Snackbar・ダイアログの使い方。基準は [design/ui.md](design/ui.md) に書く。
- 既存のリスト一覧・リスト詳細に適用する。
- **完了条件**: 既存の2画面のスクリーンショット（端末がダークモードの場合も含む）を確認してもらい、了承を得る。

## デザイン刷新（フェーズ2の前）

承認済みのデザイン（[design-tokens.md](design-tokens.md)、[implementation-spec.md](implementation-spec.md)、[design/screens/](design/screens/)）に合わせて、既存の画面を作り直し、新しい機能を加える。Repository はインメモリのまま。

- テーマ: design-tokens.md の配色・文字・角丸・余白。アプリアイコンの背景と SplashScreen を `#FFF7FF` にする。
- `domain` のモデルに公開範囲（`visibility`）と備考（`memo`）を加える。インメモリ Repository は、ログインしていない1人の利用者を本人として扱う。
- リスト一覧: 2列のカード、件数の3状態と進捗バー、鍵アイコン、リスト作成のボトムシート（名前・公開範囲・メモ）、空の状態、グリッドでの並べ替え。
- リスト詳細: 上部のメニュー（リストの編集・削除）、買い物進捗、項目のカード（数量・単位のバッジ、備考、鍵アイコン、「編集」「削除」「元に戻す」）、スワイプの色。
- 商品の追加: サジェストのシート（中身は空でよい）、Enter と「＋」による即追加と連続入力、商品詳細入力画面（新規・編集）、直前の公開範囲の引き継ぎ。
- `AddItemReducer` を新しい状態遷移に置き換え、商品詳細入力の検証と公開範囲の引き継ぎを `domain` の純粋関数にしてテストする。
- メンバーのアバターと「追加先: スーパー（共有リスト 3人）」の人数は、メンバーの情報がそろうフェーズ2で表示する。
- **完了条件**: リスト一覧（通常・空・オフライン）、リスト詳細、サジェストのシート、商品詳細入力画面のスクリーンショットを確認してもらい、了承を得る。reducer と純粋関数のテストが通る。

## フェーズ2: 認証・家族グループ・同期

- 実装の前に、家族とアカウントの画面（ログイン、家族の作成・参加、招待コードの入力、参加の確認、家族）とリスト一覧の上部バーのアバターを Stitch でデザインし、了承を得る（指示文は [stitch-prompt-family.md](stitch-prompt-family.md)）。
- Firebase プロジェクトの設定（`google-services.json` の配置、SHA-1/SHA-256 の登録）。
- Credential Manager による Google ログイン、`users/{uid}`、ログアウト。
- 家族の作成、招待（リンクとコードの発行、共有シートでの送信、リンクからの参加、コード入力での参加、取り消し）、家族画面（メンバー一覧）、オーナーによるメンバー削除、家族からの離脱とオーナーの引き継ぎ、ほかの家族への合流（リスト・項目・商品を写す）、アカウントの削除。
- App Links と Firebase Hosting（`cartmate.cheesecomer.com` の DNS 設定を含む。招待リンクとアカウント削除の案内ページ）。App Check（Play Integrity）。
- Firestore Repository（lists, items, products の最小構成。公開範囲で分けた購読）、Snapshot Listener、オンライン判定とオフラインバナー。
- メンバーのアバター（リスト一覧・リスト詳細）と、商品詳細入力画面の共有人数。
- `firestore.rules` と `firestore.indexes.json`、rules-test（家族・招待・離脱と引き継ぎ・合流・アカウントの削除・リスト・項目作成・公開範囲の部分）。
- **完了条件**: 2つのアカウントが同じ家族に参加し、追加した内容が相互に反映される。プライベートなリストと項目は、もう一方に表示されない。離脱・メンバーの削除・アカウントの削除のあと、それぞれの端末が要件どおりの画面になる。自分しかいない家族からほかの家族に合流すると、リストと項目が合流先に移る。rules-test が通る。

## フェーズ3: 購入履歴と商品

- チェック・Undo のトランザクションと、対応するルール。
- 合流で購入の記録も写す（ルールと rules-test を含む）。
- 保留チェック（DataStore, PendingCheckSyncer, WorkManager）と、サーバーの状態に保留を重ねた表示。
- `NameNormalizer`、決定的な productId、ProductGraph、表記ゆれのチップ（商品詳細入力画面）、商品の統合画面。
- リスト削除の表示ルール。
- 他のメンバーによるチェックの通知と、チェック済みの項目へのチェックした人・時刻の表示。
- rules-test（チェック・Undo・購入履歴・product）、同時実行テスト（[testing.md](testing.md#同時実行) の 1〜4, 7〜10）。
- **完了条件**: 同時にチェックしても購入履歴が重複しない。Undo で無効化される。オフラインでのチェックが接続後に確定する。リストを削除しても購入履歴が残る。

## フェーズ4: 予測とサジェスト

- CycleEstimator、ListSimilarity、SuggestionEngine、EarlyPurchaseDetector と、その単体テスト。
- サジェストのシートの中身（時期が近い商品・補完・「追加済み」・前回の数量と単位）、補完候補と商品詳細入力画面の注意表示と前回の購入、備考の候補、補足テキスト。
- 購入履歴の購読（365日分）。
- テストデータの投入スクリプト。
- **完了条件**: domain のテストが通る。テストデータで、3回目の購入から予測が出ることを画面で確認できる。

## UI の仕上げ（フェーズ5の前）

- すべての画面を通して、アニメーション、空の状態、細部の余白や文言を整える。

## フェーズ5: 受け入れ

- 同時実行テストの残り（5〜6）、Compose UI テスト。
- 実機2台での受け入れチェックリスト（[要件](requirements.md) §10 の全項目、再接続、権限、誤操作、IME、TalkBack、文字サイズ200%）。
- 読み取り数の計測（Firebase コンソール）。
- **完了条件**: チェックリストがすべて合格。
