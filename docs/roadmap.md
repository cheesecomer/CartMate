# ロードマップ

MVP は5つのフェーズに分けて実装します。各フェーズの終わりに動作とコードをレビューしてから、次に進みます。

## フェーズ1: 基盤とローカル状態の UI

- Gradle 構成（`app`, `domain`）、Version Catalog、Hilt、テーマ、Navigation。
- テスト基盤と CI: `domain` と `app` の単体テスト（JUnit、Truth、coroutines-test、Turbine）、Compose UI テスト、GitHub Actions（単体テストと lint）。rules-test と Firestore エミュレータを使う結合テストの基盤はフェーズ2で用意する。
- `domain` のモデルと Repository インターフェースを **最終形で** 定義する（フェーズ2で実装を差し替えるだけで済むように）。
- インメモリ Repository（チェック・Undo は [sync.md](design/sync.md) と同じ意味論。購入履歴の記録も含める）。
- 画面: リスト一覧（作成、未購入件数、空リストの削除）、リスト詳細（追加、数量・単位、チェック、Undo Snackbar、チェック済みを元の位置に打ち消し線で表示、スワイプ操作、項目の編集と削除）。
- 入力状態の reducer と IME フロー（サジェストの中身は空でよい）。
- **完了条件**: エミュレータ上で、ログインなしでリスト作成・連続追加・チェック・Undo・削除ができる。reducer のテストが通る。

## UI の土台（フェーズ1のあと・完了）

以降のフェーズで追加する画面がそろって従うよう、見た目の基準を先に決める。画面ごとの細かい作り込みはしない。配色は次の「デザイン刷新」でライラックに置き換える。

- テーマ: ブランドカラー（グリーン）から作った配色。白を基調にし、端末がダークモードでも白のままにする。端末の壁紙に合わせた配色（Dynamic Color）は使わない。クリーンな印象（広い余白、影の代わりに細い区切り線）にする。
- アプリアイコン: カートとチェックマーク。テーマアイコン（単色表示）にも対応する。
- 共通の部品の基準: 余白、行の高さ、空の状態の表示、Snackbar・ダイアログの使い方。基準は [design/ui.md](design/ui.md) に書く。
- 既存のリスト一覧・リスト詳細に適用する。
- **完了条件**: 既存の2画面のスクリーンショット（端末がダークモードの場合も含む）を確認してもらい、了承を得る。

## デザイン刷新（フェーズ2の前）

承認済みのデザイン（[design-tokens.md](design-tokens.md)、[implementation-spec.md](implementation-spec.md)、[design/screens/](design/screens/)）に合わせて、既存の画面を作り直し、新しい機能を加える。Repository はインメモリのまま。

- テーマ: design-tokens.md の配色・文字・角丸・余白。アプリアイコンの背景と SplashScreen を `#FFF7FF` にする。
- `domain` のモデルに公開範囲（`visibility`）と備考（`memo`）を加える。インメモリ Repository は、ログインしていない1人の利用者を本人として扱う。
- リスト一覧: 2列のカード、件数の3状態と進捗バー、鍵アイコン、リスト作成のボトムシート（名前・公開範囲・メモ）、空の状態、グリッドでの並べ替え。
- リスト詳細: 上部のメニュー（リストの編集・削除）、買い物進捗、項目のカード（数量・単位のバッジ、備考、鍵アイコン、「編集」「削除」「元に戻す」）、スワイプの色。
- 商品の追加: サジェストのシート（中身は空でよい）、Enter と「＋」による即追加と連続入力、商品詳細入力画面（新規・編集）、直前の公開範囲の引き継ぎ。
- `AddItemReducer` を新しい状態遷移に置き換え、商品詳細入力の検証と公開範囲の引き継ぎを `domain` の純粋関数にしてテストする。
- メンバーのアバターと「追加先: スーパー（共有リスト 3人）」の人数は、メンバーの情報がそろうフェーズ2で表示する。
- **完了条件**: リスト一覧（通常・空・オフライン）、リスト詳細、サジェストのシート、商品詳細入力画面のスクリーンショットを確認してもらい、了承を得る。reducer と純粋関数のテストが通る。

## フェーズ2: 認証・家族グループ・同期

- 実装の前に、家族とアカウントの画面（ログイン、家族の作成・参加、招待コードの入力、参加の確認、家族）とリスト一覧の上部バーのアバターを Stitch でデザインし、了承を得る（最終稿: [family-screens-spec.md](family-screens-spec.md) と [design/screens/](design/screens/)）。
- Firebase プロジェクトの設定（`google-services.json` の配置、SHA-1/SHA-256 の登録）。
- Credential Manager による Google ログイン、`users/{uid}`、ログアウト。
- 家族の作成、招待（リンクとコードの発行、共有シートでの送信、リンクからの参加、コード入力での参加、取り消し）、家族画面（メンバー一覧）、オーナーによるメンバー削除、家族からの離脱とオーナーの引き継ぎ、ほかの家族への合流（リスト・項目・商品を写す）、アカウントの削除。
- App Links と Firebase Hosting（`cartmate.cheesecomer.com` の DNS 設定を含む。招待リンクとアカウント削除の案内ページ）。App Check（Play Integrity）。
- Firestore Repository（lists, items, products の最小構成。公開範囲で分けた購読）、Snapshot Listener、オンライン判定とオフラインバナー。
- `NameNormalizer` の機械的な正規化と決定的な productId（Firestore の項目に productId が必要なため、フェーズ3から前倒し）。
- チェック・Undo と購入の記録を、オフラインでもできるバッチ書き込みで行う（項目を Firestore に替えてもチェックできるよう、フェーズ3から前倒し。docs/design/sync.md）。
- 参加・合流、招待の発行と取り消し、メンバーの削除、家族からの離脱、アカウントの削除、ログインを除くすべての操作を、オフラインでもできるようにする。
- 商品詳細入力画面の共有人数（リスト一覧・リスト詳細のメンバーのアバターは、冗長なため表示しないことにした）。
- `firestore.rules` と `firestore.indexes.json`、rules-test（家族・招待・離脱と引き継ぎ・合流・アカウントの削除・リスト・項目作成・公開範囲の部分）。
- **完了条件**: 2つのアカウントが同じ家族に参加し、追加した内容が相互に反映される。プライベートなリストと項目は、もう一方に表示されない。離脱・メンバーの削除・アカウントの削除のあと、それぞれの端末が要件どおりの画面になる。自分しかいない家族からほかの家族に合流すると、リストと項目が合流先に移る。rules-test が通る。

## フェーズ3: 購入履歴と商品

- 合流で購入の記録も写す（ルールと rules-test を含む）。
- ほかの端末が先にチェックしていて書き込みが拒否された場合の通知（アプリを開いている間）と、オフラインのまま7日を過ぎたチェックの通知。
- ProductGraph、表記ゆれのチップ（商品詳細入力画面）、商品の統合画面（`NameNormalizer` と決定的な productId はフェーズ2で作成済み）。
- 名寄せ辞書（[suggestions.md](design/suggestions.md#名寄せ辞書)）: 辞書の元データとビルド時の検証、実機での計測、`ProductResolver`（理由つき）、`dictionaryOptOut` とルール、統合画面での理由の表示と分離。辞書の中身は、利用許諾を確かめた出典で食品・日用品から拡充する。
- リスト削除の表示ルール。
- 他のメンバーによるチェックの通知と、チェック済みの項目へのチェックした人・時刻の表示。
- rules-test（チェック・Undo・購入履歴・product）、同時実行テスト（[testing.md](testing.md#同時実行) の 1〜4, 7〜10）。
- **完了条件**: 同時にチェックしても購入履歴が重複しない。Undo で無効化される。オフラインでのチェックが接続後に確定する。リストを削除しても購入履歴が残る。

## フェーズ4: 予測とサジェスト

- CycleEstimator、ListSimilarity、SuggestionEngine、EarlyPurchaseDetector と、その単体テスト。周期のグループ、補完の一致の理由、`suggestionExcluded` と除外の解除。商品名と備考からの属性の取り出しと、属性を使った名寄せ（`attributes.csv`、`default` の同義語。[suggestions.md](design/suggestions.md#商品名と備考による判定フェーズ4)）と、その正例・負例。商品ごとの購入履歴と、購入の記録の「予測に使わない」（`excludedFromPrediction`、ルールと rules-test を含む）。候補と「前回: …」に出す名前（統合された商品の名前は使わず統合先の名前）と、非表示の商品の扱い（候補・提案に出さない、非表示にする前の記録を予測に使わない）。
- サジェストのシートの中身（時期が近い商品・補完・「追加済み」・前回の数量と単位）、補完候補と商品詳細入力画面の注意表示と前回の購入、備考の候補、補足テキスト。
- 購入履歴の購読（365日分）。
- テストデータの投入スクリプト。
- **完了条件**: domain のテストが通る。テストデータで、3回目の購入から予測が出ることを画面で確認できる。

## UI の仕上げ（フェーズ5の前）

- すべての画面を通して、アニメーション、空の状態、細部の余白や文言を整える。
- 商品まわりの画面（商品名の管理・商品・購入履歴・商品をまとめる）を docs/design/screens/item_* のデザインにそろえる（済み）。あわせて、商品名の管理とまとめる画面の検索、まとめる画面でのメンバーの編集（外すと解除）と「すべて解除」、まとめる件数の上限の撤廃（書き込みを分けて送る）を入れた。
- 購入の記録の購読を1つにまとめる（期間の開始を日付にそろえて、画面ごとに同じ条件の購読にする。Firestore の読み取りが画面の数だけ重ならないように）。

## あとで検討する候補

採用は見送ったが、使ってみて必要になれば検討するもの。

- **購入を家族から隠す（自分のみにする）**: 自分用に繰り返し買う物を共有のまま買ってしまった場合に、自分の周期の予測を残したまま家族から隠す。今は自分の購入を項目ごと削除できる（[要件](requirements.md) §4.1「購入の削除」）。削除と比べて、ほかのメンバーが作った項目を扱えないので見送った（2026-10-28）。

- **チェック済みを手で片付ける**: のこりが0件になったら、リスト詳細に「買い物完了！ チェック済みを片付ける」を表示し、押すと前回の買い物のチェック済みを片付ける。今は、買い終わったリストに項目を追加した時点で自動で片付けている（[要件](requirements.md) §3.2「前回の買い物の片付け」）。自動の片付けで足りないと感じた場合に、手で片付ける操作を足す（2026-10-26）。

## フェーズ5: Play Console の準備

- Play Console へのアプリの登録、Play App Signing とアップロード鍵（鍵とパスワードはリポジトリに含めない）、内部テストのトラック。
- データセーフティの申告、プライバシーポリシーとアカウント削除の案内ページ（Hosting）。
- Play Integrity と Firebase App Check をつなぎ、Firestore で App Check を強制する（[security.md](design/security.md#app-check)）。
- **完了条件**: 内部テストから入れたリリース版が、App Check を強制した状態で使える。

## フェーズ6: AI による名寄せの候補

- 使うモデルの今の料金と、実際のプロンプトで計ったトークン数で、費用を試算し直す。
- Blaze プランへの切り替え、予算アラート（少しでも課金されたら知らせる）、関数のイメージの自動削除。
- `nameJudgements`・`aiUsage`・`config/ai` のデータとルール、rules-test。
- 名寄せの関数（Secret Manager の API キー、ログインと App Check とメンバーの確認、入力と応答の形の検証、月1ドルと家族ごとの上限、止める設定）と、そのテスト（エミュレータ、外部 API は偽物）。
- アプリ: 購入のあとに非同期で判定を頼む、AI の候補（表記ゆれのチップと商品名の管理、理由の表示、「この候補を出さない」）、失敗しても辞書と購入履歴だけで動くこと。
- AI の判定の正例・負例と、精度を確かめるスクリプト。
- 設計: [suggestions.md](design/suggestions.md#ai-による名寄せの候補フェーズ6)、[security.md](design/security.md#ai-の名寄せの関数)、[data-model.md](design/data-model.md#ai-の名寄せフェーズ6)。
- **完了条件**: 辞書にない表記ゆれ（「胡麻ドレ」と「ごまドレッシング」など）が候補として出て、選ぶとまとまる。上限に達したときと止める設定のときに AI を呼ばず、アプリが辞書と購入履歴だけで動く。

## フェーズ7: 受け入れ

- AI の名寄せの候補が出ること、AI を止めた・上限に達した・通信できないときに辞書と購入履歴だけで動くこと。

- 同時実行テストの残り（5〜6）、Compose UI テスト。
- 実機2台での受け入れチェックリスト（[要件](requirements.md) §10 の全項目、再接続、権限、誤操作、IME、TalkBack、文字サイズ200%）。
- 読み取り数の計測（Firebase コンソール）。
- **完了条件**: チェックリストがすべて合格。
