# セキュリティ

## Security Rules の方針

- 家族の領域（`households/{hid}` 以下）のドキュメントは、`members/{request.auth.uid}` が存在するときだけ読み書きを許可する。
- **公開範囲**: `visibility == "private"` のリスト・項目は `createdBy`、購入履歴は `purchasedBy` が本人のときだけ読み書きを許可する。プライベートのリストには、本人がプライベートの項目だけを追加できる。`visibility` はあとから変更できない（[要件](../requirements.md) §3.4）。
- **状態遷移をルールで強制する**。項目の open→completed は、同じ書き込みの中で `purchases/{itemId}` が `active == true` になる場合に限って許可する（`getAfter`）。逆方向（Undo）も同じ扱いにし、チェックした本人（`completedBy == 自分`）に限る。クライアントにバグがあっても、「チェック済みなのに購入履歴がない」「Undo したのに履歴が有効なまま」という状態は作れない。
- サーバー時刻を強制する（`createdAt/completedAt/purchasedAt == request.time`）。購入日時の改ざんや、端末の時計のずれを防ぐ。端末時刻の `checkedAt` だけは、許容範囲（未来5分〜過去7日）を検証して受け付ける（[sync.md](sync.md#オフラインの書き込み)）。
- フィールドを `keys().hasOnly(...)` で制限し、型と長さを検証する。
- 編集: 未購入の項目の商品名・数量・単位・備考と、リストの名前・備考だけを変更できる。チェック済みの項目は、購入の記録と食い違わないよう変更できない。
- 削除: 家族と商品は削除できない。購入の記録は、チェックした本人が、項目と同じ書き込みでだけ削除できる（チェック済みなのに購入の記録がない状態を作らない。項目がもうない場合は購入の記録だけ消せる）。リストは論理削除のみ。物理削除できるのは未購入の項目だけ（誤って追加したものの取り消し。[ui.md](ui.md#スワイプ操作)）。例外として、アカウントの削除では本人のプライベートなリスト・項目・購入の記録を物理削除できる。
- 招待コードは `get`（IDを指定した読み取り）だけを許可し、一覧の取得は同じ家族のメンバーに限る。参加処理は、「members の作成」と「invite の usedCount +1」が同じバッチに含まれる場合だけ成立させる。

## ルール

ルールは [firebase/firestore.rules](../../firebase/firestore.rules) にあり、[firebase/rules-test/](../../firebase/rules-test/) で検証します（[testing.md](../testing.md#rules-test)）。ルールを変えたら、rules-test も更新します。

1回の書き込みで評価される `get/exists` は、購入完了のトランザクションで最大4件程度です（上限は20件）。

オーナーの引き継ぎで「参加がいちばん早いメンバー」を選ぶことは、ルールでは検証できません（コレクションを数えたり並べたりできないため）。ルールが保証するのは「オーナーが抜けるバッチでだけ、ほかのメンバーをオーナーにできる」ことまでで、相手の選び方はクライアントに任せます。オーナーが残りのメンバーを引き継がずに抜けることもルールでは防げませんが、その場合もメンバー削除ができなくなるだけで、データは守られます。

プライベートな項目は、作った本人しか読めない（＝チェックできない）ため、その購入履歴の `purchasedBy` は必ず項目を作った本人になります。そのため、購入履歴の公開範囲の判定には `purchasedBy` を使えます。

## 招待

### 招待コード

- 10文字、Crockford Base32（読み間違えやすい文字を含まない）。表示するときは `7KQ2-M9XP-HA` のように区切る。
- 有効期限は24時間、使えるのは1回だけ。1人につき1つ発行する。
- 招待を発行できるのは家族のメンバー全員。発行したコードは、同じ家族のメンバーなら取り消せる。
- 商品の統合（[data-model.md](data-model.md)「統合は1段にし、変更は1つのバッチで書く」）: 統合は、未統合の商品を未統合の商品にだけ行え、最初に統合した人と時刻（`mergedBy`・`mergedAt`）を書く。統合済みの商品の統合先を直接変えることはできない。付け替えは、今の統合先が同じバッチの中で解除される（その元の統合先へ移す）か、新しく統合される（同じ統合先へ移す）ときだけ認め、`mergedBy`・`mergedAt` は変えられない。統合・付け替え・解除のどれでも、変えた人と時刻（`mergeUpdatedBy`・`mergeUpdatedAt`）を書く。ルールが1回の書き込みで読めるドキュメントは20件までなので、1つのバッチでルールが読む商品は18件まで（メンバーの確認と統合先で2件、ほかの商品をまとめている商品の統合や、下に商品がある商品の解除で1件ずつ）。「商品をまとめる」はこれを超える分を次のバッチに分けて送るので（`ProductMerge.editChanges`）、画面には上限がない。
- 名前の訂正: 統合先は、同じ書き込みの中で作る商品か、同じ書き込みで統合を外す商品でもよい（統合のルールは、書き込んだあとの統合先が未統合であることを確かめる）。
- 予測に使わない: 購入の記録の `excludedFromPrediction` は、その記録を読める人（共有は家族の誰でも、プライベートは本人だけ）が切り替えられる。予測に使わないにするときは外した人と時刻（`excludedBy`・`excludedAt`、サーバー時刻）を書き、戻すときは消す。ほかのフィールドは一緒に変えられない。
- 常に非表示: 商品の `suggestionExcluded` は、メンバーなら誰でも切り替えられる。常に非表示にするときは設定した人と時刻（`suggestionExcludedBy`・`suggestionExcludedAt`、サーバー時刻）を書き、解除するときは消す。ほかのフィールドは一緒に変えられない。名前の訂正で作る商品は、同じ条件で最初から常に非表示にして作れる。
- 商品の非表示: 統合先の商品だけを、メンバーなら誰でも非表示にでき、非表示にした人と時刻（`hiddenBy`・`hiddenAt`、サーバー時刻）を書く。「表示する」は両方を消す。ほかのフィールドは一緒に変えられない。
- 表示名と呼び名（[data-model.md](data-model.md)）: `members/{uid}` は、本人が自分の `nickname`（20文字まで）だけを変更・解除できる。ほかの人の `members` の `nickname` は変更できない。`users/{uid}` の `nickname` と `memberAliases` は本人だけが読み書きでき、`memberAliases` は100件まで。
- 招待には発行した人の表示名（`inviterName`）を写す。参加前のユーザーは `members` を読めないため、参加の確認画面の「○○さんの家族」はここから表示する。

### 招待リンク（App Links）

リンクならタップするだけで参加できるため、コードと併用します。コードは、アプリが未インストールのときなどの予備として残します。

- **URL**: `https://cartmate.cheesecomer.com/join/{code}`
- 招待を発行すると、リンクとコードの両方を含む文面を共有シートで送ります。
  - 例: 「CartMate の家族に招待されました。https://cartmate.cheesecomer.com/join/7KQ2M9XPHA （コード: 7KQ2-M9XP-HA、24時間有効）」
- **アプリがインストール済みの場合**: App Links（`autoVerify`）でアプリが直接開きます。参加確認の画面（「○○さんの家族に参加しますか？」）を表示し、承認すると参加処理を実行します。未ログインなら、ログインしてからこの画面に戻ります。すでに家族に参加している場合は、参加せずにその旨を表示します。
- **アプリが未インストールの場合**: Firebase Hosting の静的なフォールバックページを表示します。ストアへの案内と、「アプリを入れたらこのコードを入力してください」というコードを表示します。Play Install Referrer でコードを引き継ぐ方法は使いません（ストアで公開する前は機能しないため）。
- **リンクの安全性**: リンクを開いただけでは参加しません（必ず確認画面を挟む）。LINE などのリンクプレビューが URL を読み込んでも、コードは消費されません。コードの安全性（推測しにくさ、期限、使用回数）は、コードを直接入力する場合と同じです。

**ホスティング**: サブドメイン `cartmate.cheesecomer.com` を Firebase Hosting に割り当てます。`assetlinks.json` とフォールバックページを `firebase/` 配下で一緒に管理でき、デプロイも Firebase CLI だけで済みます。`cheesecomer.com` 本体のサイト構成にも影響しません。

| ファイル | 内容 |
|---|---|
| `firebase/hosting/.well-known/assetlinks.json` | パッケージ名と署名証明書の SHA-256 フィンガープリント（デバッグ用、アップロード鍵、Play App Signing の鍵） |
| `firebase/hosting/join/index.html` | フォールバックページ（`/join/**` をこのページに rewrite する） |
| `firebase/hosting/account-deletion/index.html` | アカウント削除の案内ページ（Play Console のデータ削除の URL に登録する） |

## メンバー管理

- オーナーは、自分以外のメンバーを家族から削除できます。招待コードが意図しない人に渡った場合の、最低限の対処です。
- メンバーは自分で家族から抜けられます。オーナーが抜けるときは、`joinedAt` がいちばん早いメンバーにオーナーを引き継ぎます（同じバッチ）。引き継ぐ相手を選んでの譲渡は MVP の対象外です。

## ほかの家族への合流

家族に自分しかいない人が、ほかの家族に移る機能です（[要件](../requirements.md) §3.5）。

- 手順: ①招待コードで合流先に参加する（`members` の作成と招待の `usedCount` +1。`users` はまだ変えない） → ②コピー元の products → lists → items → purchases の順に、同じIDで合流先に写す（`importedFrom` を付ける） → ③`users/{uid}.householdId` を合流先にし、元の家族の自分の `members` を削除する（同じバッチ）。
- 所属（`users`）を最後に切り替えるのは、切り替えた時点で画面がリスト一覧に移るためです。写している途中で画面が切り替わって処理が止まらないようにします。
- 「自分しかいない」ことはルールでは確かめられないため、クライアントで `members` の件数を見て判定します。ほかのメンバーがいる家族から写しても、写せるのは本人がもともと読めるデータだけなので、データは漏れません。
- ①のあとで中断した場合に備えて、合流元と合流先を端末に記録しておき（`FamilyMerger`）、次に起動したときに②から再開します。すでに写したドキュメントは飛ばします。
- ルールの `get` は1回の書き込み（バッチ）で20件までです。合流では、2つの家族のメンバー確認（2件）とコピー元の読み取り（1件ずつ）を使うので、1つのバッチで写せるのは18件までです。購入の記録が多いと書き込みの回数が増えるため、進み具合を表示します。
- 購入の記録を写す処理は、Firestore に購入の記録を書くフェーズ3で加えます。

## アカウントの削除

Google Play は、アカウントを作るアプリに、アプリ内とアプリ外（Web）の両方から削除できる手段を求めます。

- アプリ内: 家族画面の「アカウントを削除」。Firebase Auth の削除には直近のログインが必要なため、先に Google で再ログインしてもらいます。
- 削除の順番: ①本人のプライベートなリスト・項目・購入の記録を削除 → ②離脱（オーナーなら引き継ぎ） → ③`users/{uid}` を削除 → ④Firebase Auth のユーザーを削除。途中で失敗した場合は、もう一度実行すれば続きから削除できるようにします（どの手順も、すでに消えていれば何もしない）。
- Cloud Functions は使わず、アプリから削除します（関数は AI による名寄せの候補にだけ使う。[要件](../requirements.md) §2）。
- アプリ外: Hosting の案内ページに、アプリからの削除手順と、アプリを使えない場合の連絡先を載せます。

## AI の名寄せの関数

フェーズ6で作ります（[suggestions.md](suggestions.md#ai-による名寄せの候補フェーズ6)）。アプリに API キーを入れず、Cloud Functions（呼び出し可能な関数）から外部の AI API を呼びます。

- API キーは Secret Manager に置き、関数だけが読む。
- 呼び出しには、ログインと App Check（強制）を求める。関数は、呼んだ人が家族のメンバーであることを確かめる。
- 入力（正規化した商品名と、規則で読み取った属性）の長さと形を確かめ、AI の応答も決めた形（品目・形態・容量・用途・種類・信頼度・理由）かを確かめる。形が違えば判定を失敗にする。
- 費用の上限: 関数が月ごとの使用量（実際のトークン数 × 単価で求めた金額）と家族ごとの回数を数え、全体で月1ドル・家族ごとに月100回を超えたら AI を呼ばない。上限の80%と100%で知らせる。
- 止める設定: `config/ai.enabled` が false なら AI を呼ばない（Firebase のコンソールから切り替える）。
- 判定（`nameJudgements`）と使用量（`aiUsage`）、設定（`config/ai`）は関数だけが書ける。判定は家族のメンバーが読める。
- Firebase は Blaze プランにするが、無料枠に収める。予算アラートで少しでも課金されたら知らせ、関数のイメージ（Artifact Registry）は古いものを自動で消す。

## App Check

Firebase App Check（Play Integrity）を導入します。招待コードの総当たりや、改造したクライアントからのアクセスを、少ない手間で抑えられます。

- リリース版は Play Integrity、デバッグ版はデバッグ用のプロバイダを使います（`app/src/release`、`app/src/debug` の `AppCheckSetup`）。デバッグ版は、起動時に Logcat（`DebugAppCheckProvider`）に出るトークンを Firebase コンソールの App Check に登録します。
- Firestore での App Check の強制は、Play Console にアプリを登録して Play Integrity を Firebase とつないでから有効にします。それまでは強制しません（強制すると、登録のない端末から読み書きできなくなるため）。

## リポジトリに含めないもの

- `google-services.json`: 秘密情報ではありませんが、公開リポジトリには含めず、各自の Firebase プロジェクトから取得します。
- 署名鍵（keystore）とそのパスワード。
