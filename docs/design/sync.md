# 同期・チェック/Undo・オフライン

## 用語

画面上ではすべて「チェック」「チェック済み」と表記します。チェックは「カゴに入れた時」に行うのが普通ですが、別の場所で買って帰宅後にチェックする場合もあるため、どちらにも当てはまる表現にしています。

コード上の名前（`completed`, `purchases`）は「購入」のままです。予測から見れば購入の記録であることに変わりがないためです。

## チェック（購入完了）

`completeItem(itemId, checkedAt)` は、項目の更新と購入の記録を **1つのバッチ書き込み** で行います。バッチはオフラインでも Firestore の書き込みキューに積まれ（アプリを閉じても残る）、接続が戻ると送られます。書いた時点で端末のキャッシュに反映されるので、画面はすぐにチェック済みになります。

```
batch {
  update(items/itemId, status=completed, completedAt=serverTimestamp, completedBy=me)
  set(purchases/itemId, {itemId, listId, listNameSnapshot=list.name, productId, inputName,
                         quantity, unit, memo, visibility, checkedAt, purchasedAt=serverTimestamp,
                         purchasedBy=me, active=true, revokedAt=null, revokedBy=null})
}
```

- 書き込む値（リスト名、商品、数量など）は、端末のキャッシュにある項目とリストから作ります。
- **購入履歴が二重にできない理由**: 購入履歴のIDは itemId です。ルールは「未購入の項目しかチェックできない」「購入の記録とそろった書き込みでしかチェックできない」を強制するので、先にほかの端末がチェックしていれば、後から届いた書き込みは拒否されます。
- **Undo したあとの再チェック**: 同じ `purchases/{itemId}` を `active=true` と新しい `purchasedAt` で上書きします。取り消した購入は残しません。
- 戻り値: `sealed interface CompleteResult { Completed; AlreadyCompleted(by, at); Retry; Rejected(e) }`
  - キャッシュの項目がすでにチェック済みなら、書き込まずに `AlreadyCompleted` を返します。それ以外は書き込みをキューに積んで `Completed` を返します。
- 書き込みがサーバーで拒否された場合（ほかの端末が先にチェックしていた、など）は、アプリを開いていれば、項目を読み直して「牛乳は 花子さんが 10:02 にチェック済みです」と表示します（[ui.md](ui.md#他のメンバーによるチェックの通知)）。アプリを閉じている間に拒否された場合は通知できませんが、表示はサーバーの状態に戻り、購入履歴が二重になることはありません。

## Undo

`reopenItem(itemId)` も、項目と購入の記録を1つのバッチ書き込みで更新します。

```
batch {
  update(items/itemId, status=open, completedAt=null, completedBy=null)
  update(purchases/itemId, active=false, revokedAt=serverTimestamp, revokedBy=me)
}
```

- キャッシュの項目がすでに未購入なら、書き込まずに `AlreadyOpen` を返します。
- 予測には `active == true` の購入だけを使うため、Undo するとそのまま予測の対象から外れます。
- Undo は家族の誰でもできます。
- Undo の入口は3つです。①チェック直後の Snackbar（約5秒）。②リスト詳細のチェック済みの項目の「元に戻す」ボタンか ← スワイプ（直近24時間は元の位置に表示されるので、画面を移動したあとでも確認・取り消しができる）。③チェック済みの項目のタップ。
- オフラインでチェックしてから Undo した場合も、2つの書き込みが順に送られ、ルールで順に確かめられるので、正しく元に戻ります。

## 競合の振る舞い

| シナリオ | 結果 |
|---|---|
| A と B が同じ項目を同時にチェック | 先にサーバーに届いた方が残り、後の書き込みは拒否される。後の端末には「牛乳は 花子さんが 10:02 にチェック済みです」と表示する（アプリを開いていれば）。有効な購入履歴は1件 |
| A がチェック → B が Undo → A が Snackbar から Undo | A の端末のキャッシュがすでに未購入なら `AlreadyOpen` になり、「すでにチェックが外されています」と短く表示する。まだ反映されていなければ、A の Undo はルールで拒否される |
| A が Undo、同時に B が再チェック | 書き込みはサーバーで順に確かめられ、項目の状態と購入履歴の active は必ず一致する |
| チェックと未購入項目の削除が同時 | 削除のルールが `status == 'open'` を要求するので、先に届いた方が勝つ |
| 編集中に他のメンバーがその項目をチェック | 編集のルールも `status == 'open'` を要求するので、更新は拒否される。編集した人には「牛乳 はチェック済みのため変更できません」と表示する |
| 編集中に他のメンバーがその項目を削除 | 更新は失敗し、「編集していた商品は削除されています」と表示する |
| A がオフラインでチェック → その間に B がオンラインでチェック → A が接続復帰 | A の書き込みは拒否される。A がアプリを開いていれば「牛乳は 花子さんが 10:02 にチェック済みです」と表示する。通知は接続が戻るまで遅れる |
| オフラインのまま7日を過ぎたチェック | ルールが `checkedAt` を過去7日までしか受け付けないので拒否され、「牛乳のチェックを反映できませんでした」と表示する（アプリを開いていれば） |

## オフラインの書き込み

店内は電波が弱いことが多く、チェックはカゴに入れた時点で行われるのが普通です。そのため、**参加・合流、招待の発行と取り消し、メンバーの削除、家族からの離脱、アカウントの削除、ログインを除くすべての操作を、オフラインでも行えるようにします**（[要件](../requirements.md) §3.3）。書き込みは Firestore の書き込みキューに積み、完了を待たずに画面を進めます。

- 書き込みの前提になる情報（ログイン中のユーザーと家族、並び順、リスト名など）は、端末のキャッシュとアプリの中で共有している購読から取り、サーバーには問い合わせません。
- **周期の計算には `checkedAt` を使う**ため、オフラインでチェックして日付をまたいで送られても、購入日はずれません。`purchasedAt` は送られた時刻（サーバー時刻）になります。
- キューに積んだ書き込みがルールで拒否された場合は、アプリを開いていれば Snackbar で知らせます。

| 操作 | オフライン | 理由 |
|---|---|---|
| リスト・項目・履歴の閲覧 | 可 | 永続キャッシュ |
| 項目の追加（product の作成を含む）・編集・削除 | 可 | product ID が決定的なので重複しない。送られたときにチェック済みなら、編集と削除はルールで拒否されるだけ |
| チェック / Undo | 可 | 上記のバッチ書き込み。冪等性はルールで保証する |
| リストの作成・編集・削除、並び替え | 可 | 削除は「未購入が0件」を端末のキャッシュで判定する。古い判定で削除しても、未購入の項目があるリストは一覧に表示し続ける（下記の表示ルール） |
| 家族の作成、商品をまとめる・解除する | 可 | 書き込みは接続が戻ると送られる。家族を作ったその場で、オフラインのままリストを作り始められる |
| 参加・合流 | **不可** | 招待コードが有効か（存在・期限・未使用）と招待した人の名前を、サーバーで確かめる必要がある |
| 招待の発行 | **不可** | 招待された人がコードを入力するのに通信が必要で、オフラインで発行しても、送られるまで使えない |
| 招待の取り消し | **不可** | 取り消しがサーバーに届くまではそのコードで参加できてしまい、取り消したつもりでも参加を防げない。間に合わずに参加された場合は、オーナーがメンバーを外す |
| メンバーの削除 | **不可** | 削除がサーバーに届くまでは、外したはずの人がリストを読み書きできてしまい、外したつもりになる |
| 家族からの離脱 | **不可** | オフラインで抜けても、その後の参加には通信が必要で利点がない。オーナーの引き継ぎ先（参加がいちばん早いメンバー）を古い情報で選ぶおそれもある |
| アカウントの削除 | **不可** | Google での再ログインと Firebase Auth の削除に通信が必要。消すべきプライベートなデータも、サーバーに問い合わせて探す |
| ログイン | **不可** | Google でのログインに通信が必要 |

### オンライン判定と表示

- `ConnectivityManager.NetworkCallback` で `NET_CAPABILITY_VALIDATED` を監視し、`Flow<Boolean>` で提供します（`OnlineStatus`）。
- オフラインの間は、上部のバーの直下にバナー（「オフライン表示中（変更は再接続時に同期されます）」、背景 `WarningBannerBackground`、文字とアイコン `WarningBannerText`）を表示します。
- 未同期のもの（Firestore の書き込みキューにある書き込み＝`hasPendingWrites`）には、小さな「未同期」アイコンを付けます。
- オフラインでできない操作をしようとした場合は、理由を伝えます。

## 商品の統合の競合

商品をまとめる・解除するは、1つのバッチで書きます。バッチは原子的ですが、端末で読んだ統合関係が、書き込みがサーバーに届いた時点でも正しいとは限りません（オフラインの間にほかのメンバーが変えた場合など）。整合性はルールで保ちます（[security.md](security.md)）。

| シナリオ | 結果 |
|---|---|
| A が中間の商品を解除（その下の商品を付け替える）、その前に B がその下の商品を解除していた | 付け替えの前提（今の統合先が解除される商品であること）が崩れているので、A のバッチはまるごと拒否される。B が外した商品をまとめ直すことはない |
| B がその下の商品を解除、その前に A が中間の商品を解除していた | どちらも反映され、2件とも外れる |
| A と B が逆向きに同時にまとめる | 統合先は未統合でなければならないので、後から届いた方が拒否される。循環しない |
| A がほかの商品をまとめている商品をまとめる、その前に B がその下の商品を解除していた | A のバッチはまるごと拒否される。選んだほかの商品だけがまとまることはない |

- 拒否されると、Firestore が端末の表示をサーバーの状態に戻します。書き込みの成否はリポジトリ（アプリ全体で1つ）で受け取り、アプリ全体の通知（Toast）で「商品のまとめ方を変更できませんでした。ほかのメンバーが先に変更しています」と知らせます。画面を移ったあとでも知らせられます。
- アプリを閉じている間に拒否された場合に備えて、書き込むときに期待する統合先を端末に記録しておきます。確定したら消し、次に起動したときに残っていれば、書き込みのキューを送り終えてからサーバーの状態と比べ、違っていれば同じように知らせます。
- アプリを閉じている間に拒否されたチェックは、今は次の起動で知らせていません（チェックの書き込みの拒否は、アプリを開いている間だけ知らせる）。

## リスト削除の競合

- 削除は、UI ではリスト詳細のメニューから「未購入が0件のリスト」に対してだけ提供します。すぐには削除せず、確認ダイアログを出します。オフラインでも削除でき、未購入の件数は端末のキャッシュで数えます。未購入の件数は自分に見える項目で数えるため、他のメンバーのプライベートな項目が残っているリストも削除できます。その項目は、削除済みリストの表示ルール（下記）によって、作った本人の一覧には残ります。
- **表示ルール**: `status == active` **または** そのリストに未購入の項目がある場合、一覧に表示します。
  - 削除と同時に別の端末で項目が追加された場合や、削除済みリストの項目を Undo した場合でも、項目が見えなくなることはありません。項目がすべて片付くと、再び非表示になります。
  - 買い終わったリストに項目を追加するときの、前回の買い物のチェック済みの片付け（`clearedAt`）は、項目の追加とは別の書き込みにします。削除済みのリストは変更できないので、同じ書き込みにすると、削除が先に届いたときに追加した項目まで拒否されて消えるためです。片付けだけが拒否された場合は、前回のチェック済みが表示に残ります。
- 最後の項目をチェックしても、リストは自動では削除しません（Undo との競合を避けるため）。
