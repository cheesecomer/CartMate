# 商品の同一性とサジェスト

この資料のロジックは、すべて `domain` モジュールの純粋関数として実装します。

## 商品名の正規化

`NameNormalizer` は3つのキーを作ります。

| キー | 処理 | 用途 |
|---|---|---|
| `displayName` | NFKC → 前後の空白除去 → 連続空白を1つに | 表示 |
| `normalizedName` | displayName → 英字を小文字化 | **同一性の判定**（決定的IDの元） |
| `searchKey` | normalizedName → カタカナをひらがなに → 空白・記号を除去 | **補完と類似候補の検索だけ**に使う。自動で同じ商品として扱うことはしない |

NFKC で全角・半角の差（「ｷﾞｭｳﾆｭｳ」→「ギュウニュウ」、「１Ｌ」→「1L」）を吸収します。カナの統一は、意味が変わる可能性がわずかに残るため、同一性の判定には使いません。

## 名寄せ辞書

アプリに同梱する辞書で、機械的な正規化では結び付かない表記ゆれをまとめます（[要件](../requirements.md) §4.2）。辞書の元データは `dictionary/` に置き、ビルド時に検証して、アプリのアセット（TSV）を作ります。

### 辞書の内容

| 種類 | 項目 | 用途 |
|---|---|---|
| 品目 | `canonicalId`（一度使った ID は再利用しない）、表示名 | まとめる先 |
| 別名 | 正規化したキー（`NameNormalizer.normalizedName`）→ `canonicalId`、照合の条件（`exact`：完全一致だけ／`prefix`：購入履歴の前方一致の照合にも使う／`default`：上書きできる既定の同義語） | 同じ商品の判定と、購入履歴の照合 |
| 周期グループ | `cycleGroupId`（品目とは別の名前空間）→ 品目の一覧 | 購入周期の計算だけで合算する |
| 統合禁止 | 品目の ID の組 | 辞書でも手動の候補でも、自動では同じ商品にしない |
| 属性の語（`attributes.csv`） | 語 → 種類（`item`：品目／`form`：形態／`use`：用途／`variant`：種類／`ignore`：判定に使わない）と値 | 商品名と備考から、名寄せに関係する属性を取り出す（`AttributeExtractor`） |
| 版と出典 | 辞書の版、各行の出典 | 更新の追跡と、利用許諾の確認 |

- ひらがな1〜2文字の別名（「す」「さけ」など）は `exact` に限ります。部分一致に使うと、ほかの名前（「れたす」）や同音の別の商品（酒）に当たるためです。
- 利用許諾と再配布の条件を確かめられない外部のデータは取り込みません。
- 辞書は読むときにだけ使い、`productId`・入力した名前・購入の記録は書き換えません。
- **辞書の目的は、購入履歴に登録された商品の名寄せです。** 商品のカタログや入力の予測変換ではありません（入力途中の変換は IME に任せる）。辞書に載っているだけの商品をサジェストの候補にすることはありません。件数や網羅性は目標にせず、実際の買い物で出る表記ゆれと、誤統合しやすい組を正しく扱えるかを重視します。
- 日本国内の日常の買い物の言葉を基準にします。「お茶」は緑茶を指すことが多いので、`default`（既定の同義語）として登録します。商品名や備考に「麦茶」「ほうじ茶」のような品目の語があれば、そちらを優先します。
- 外部データ（成分表、家計調査）は、語彙を見つける参考資料です。辞書には自動で取り込まず、`tools/dictionary/review.py` で確認用の一覧（`dictionary/review/`）を作り、人が見て手で足します。出典とライセンスは [dictionary/SOURCES.md](../../dictionary/SOURCES.md) にあります。
- 名前だけで判定できる正例・負例は `dictionary/tests/cases.csv` に置き、`./gradlew :domain:test` で確かめます（「さけ」「す」のような短い読みの衝突を含む）。

### 商品名と備考による判定

同じ名前の商品でも、備考で形態・容量・用途・種類が違えば、同じ商品とは限りません（「緑茶」＋「茶葉」と「緑茶」＋「2L のペットボトル」）。名寄せに関係する属性を商品名と備考から取り出して比べます。備考の全文を単純に比べることはしません。

- 取り出す属性: 品目（`attributes.csv` の `item`）、形態（茶葉・ティーバッグ・飲料・粉末）、容量（「2L」「2リットル」「500ml」のような数字と単位を規則で読む）、用途（燃えるゴミ用など）、種類（詰め替え・本体）。
- 判定に使わない語（「特売なら」「いつもの」「安いやつ」）は除きます。ブランドや具体的な商品の指定は除きません。
- **属性が未指定であることと、属性が一致することは別にします。** 片方だけに属性があれば、同じ商品と断定せず、候補にとどめます。未指定の属性を補って、具体的な商品にまとめることはしません。
- 商品名と備考の情報が食い違う場合は、まとめません。
- 判定は購入の記録ごとに行い、予測とサジェスト（`SuggestionEngine`）の集計で使います。商品名の管理の辞書の名寄せと表記ゆれの候補（`ProductResolver`）は商品名だけで判定し、`default` の同義語ではまとめません。
- 記録のまとめる先: `ProductResolver` の結果が「どれにも当たらない」で、統合先の商品名が `default` の別名（お茶）なら、商品名と備考の品目の語がなければ既定の品目、1つならその品目、2つ以上なら食い違うのでその商品のまま。辞書でまとめた商品でも、備考の品目の語が辞書の品目と違えば、その商品のまま。
- 周期は「周期のグループ（なければまとめる先）＋形態・用途・種類・容量の組」ごとに数えます。属性のない記録は、属性のある記録と別の組です。
- 容量は数字と単位（ml・l・リットル・g・kg・キロ）を読み、ml か g にそろえます。
- 「追加済み」の判定は、属性によらずまとめる先（と周期のグループ）で比べます（同じ商品がリストにあれば、属性が違っても時期が近い商品に出さない）。
- 時期が近い商品は、属性で分かれる場合に「緑茶（茶葉）」のように属性（備考の品目、形態・用途・種類、容量は「2L」）を添え、「＋」では前回の備考も一緒に入れます。補完は名前で選ぶので、属性のない記録の周期で早すぎる再購入を判定します。商品詳細入力画面の「前回: …」は、前回の購入と同じ属性の記録の周期を使います。

### 名寄せの解決

`ProductResolver.resolve(product): Resolution` は、次の順で「まとめる先」と「理由」を返します（domain の純粋関数）。

1. 手動の統合（`mergedInto`）があれば、`ProductGraph` でたどった統合先。理由は「手動」。
2. 手動で分離（`dictionaryOptOut == true`）していれば、自分自身。理由は「分離」。
3. 辞書の別名に `normalizedName` が完全一致すれば、辞書の品目。ただし、統合禁止の組に当たる場合はまとめない。理由は「辞書（一致した別名、品目）」。
4. どれにも当たらなければ、自分自身。

- 同じ辞書の品目にまとまる product どうしは、同じ商品として予測・補完・「追加済み」の判定に使います。
- 周期のグループは別に解決し（`cycleGroupOf`）、周期の計算だけで合算します。補完や「追加済み」の判定では使いません。

### 計測

`DictionaryBenchmark`（androidTest）で、合成した辞書を実機で計測します。手順は [testing.md](../testing.md#名寄せ辞書の計測) にあります。2026-10-27 に SO-54C（Android 14）で測った結果です。

| 別名の件数 | CSV | 読み込み（解析） | 保持するメモリ | 検索10万回 |
|---|---|---|---|---|
| 1万 | 319KiB | 140ms | ― | 23ms |
| 5万 | 1.6MiB | 394ms | 約3.2MiB | 16ms |
| 10万 | 3.3MiB | 729ms | 約5.7MiB | 19ms |

- 検索は1回 0.2µs 程度で、件数によらない。読み込みは起動後に別スレッドで行うので、画面の表示を待たせない（読み込み終わるまでの間は名寄せが効かないだけ）。
- APK の増加は、5万件で 0.6MiB 前後の見込み（圧縮後。実物は未計測）。
- 数万件まではメモリに読む方式のままにする。10万件を超えるか、起動直後の名寄せの遅れが問題になったら、作成済みの SQLite を読み取り専用で開く方式に移る。

## 項目を追加するときの商品の解決

1. 入力名から `normalizedName` を求め、`productId = id(normalizedName)` を計算します。
2. 同じIDの product があればそれを使います（統合されていれば、`ProductGraph` で統合先を解決します）。なければ、バッチで product と item を作成します。
3. 項目の `productId` は、**入力名に対応する product**（統合元）を指します。統合先への置き換えは読み取り時に行います。

## 表記ゆれの紐付け

意味の違う商品を誤ってまとめないよう、自動では確定しません。

- **入力時**: 商品詳細入力画面（新規）で、入力名が新しい product で、かつ `searchKey` が前方一致・部分一致する既存の商品がある場合、「『牛乳』と同じ商品として記録する」チップを表示します。初期状態は未選択です。選択した場合だけ、新しい product を `mergedInto = 牛乳の統合先` で作成します。Enter と候補の「＋」による即追加では表示しません（連続入力を止めないため）。
- **あとから**: 家族画面から開く「商品名の管理」で、統合先の商品を開いて「商品をまとめる」から複数の商品をまとめ、まとめた商品を1件ずつ解除できます（[ui.md](ui.md)）。過去に別々の商品として記録された履歴をまとめるために必要です。
- 「ぎゅうにゅう」と「牛乳」のように読みでしか結び付かないものは、名寄せ辞書に載っていれば辞書でまとめます。載っていなければ機械的には検出できないので、あとからの統合で対応します。

### ProductGraph

- `resolve(productId): ProductId` は `mergedInto` をたどって統合先を返します。たどる深さは10までとし、循環を見つけたら自分自身を返します（同時に統合操作が行われた場合の保険）。
- 統合するときは、クライアントで統合先を解決してから、その統合先のIDを書き込みます（ルールでも、統合先が未統合であることを確認します）。

## サジェストの補正

自動の判定より優先する、家族で共有する訂正です。どれも元に戻せ、記録や入力した名前は書き換えません。

| 補正 | 対象 | 保存先 | 効果 |
|---|---|---|---|
| 統合・統合の解除 | 商品 | `products.mergedInto` | 購入記録を合算する |
| 辞書の名寄せの分離 | 商品 | `products.dictionaryOptOut` | 辞書でまとめない |
| 常に非表示 | 商品（統合先） | `products.suggestionExcluded`・`suggestionExcludedBy`・`suggestionExcludedAt` | 時期が近い商品・補完・表記ゆれの候補・早すぎる再購入の注意に出さない。再購入しても戻らない。周期は数えるが出さない。名前の訂正で新しく作る商品に引き継ぐ |
| 名前の訂正 | 商品 | `products.mergedInto`（正しい名前の商品がなければ作る） | 誤字の商品を正しい名前の商品にまとめる。記録は書き換えない |
| 一時的に非表示 | 商品 | `products.hiddenAt`・`hiddenBy` | 一覧・補完・提案・表記ゆれの候補に出さず、予測に使わない。あとで使われたら自動でまた表示し、非表示にする前の記録は予測に使わない |
| 予測に使わない | 購入の記録 | `purchases.excludedFromPrediction` | 周期の推定、早すぎる再購入の検知、リスト類似度、補完の購入回数に使わない |

- 「予測に使わない」は、商品ごとの購入履歴（統合の画面から開く）で1件ずつ切り替えます。共有の記録は家族の誰でも、プライベートの記録は本人だけが切り替えられます（ルールの `canSee` と同じ）。
- 除外した記録も履歴には表示し、除外したことと、誰がいつ外したかを示します。

## パラメータ

MVP では定数とし、UI からは変更しません。

```kotlin
data class SuggestionParams(
    val minEvents: Int = 3,              // 周期予測を始める購入回数（購入日の数）
    val maxIntervals: Int = 10,          // 中央値に使う直近の間隔数
    val dueRatio: Double = 0.8,          // 未入力時サジェストの閾値
    val staleRatio: Double = 3.0,        // これを超えたら「買うのをやめた」とみなして出さない
    val earlyRatio: Double = 0.5,        // 早すぎる再購入の閾値
    val maxDispersion: Double = 0.5,     // MAD/中央値 がこれを超えたら周期が不安定
    val minProfileSize: Int = 5,         // 類似度を計算するリストの最小商品数
    val minIntersection: Int = 3,
    val minOverlap: Double = 0.5,        // 重複係数の閾値
    val maxDue: Int = 10,
    val maxCompletions: Int = 8,
)
```

## 周期推定

```kotlin
data class CycleEstimate(
    val eventDates: List<LocalDate>,   // 日付単位でまとめた購入日（昇順）
    val medianIntervalDays: Double,
    val dispersion: Double,            // 中央絶対偏差 / 中央値
) { val lastPurchase: LocalDate get() = eventDates.last() }

fun estimateCycle(purchaseDates: List<LocalDate>, params: SuggestionParams): CycleEstimate?
fun elapsedRatio(estimate: CycleEstimate, today: LocalDate): Double
```

1. 入力は、統合先が同じ product の `active` で、予測に使わないにしていない（`excludedFromPrediction != true`）購入のうち自分に見えるもの（共有と、自分のプライベート）の `checkedAt` を、端末のタイムゾーンで `LocalDate` に変換したものです。`purchasedAt` ではなく `checkedAt` を使うのは、オフラインでチェックして送られるのが日をまたいでも、実際にチェックした日を購入日にするためです。家族全体・全リストの履歴を合算します（場所によって周期を分断しない）。
2. **同じ日に複数回買った場合は、1回の購入として数えます。** 家族2人が同じ日に買った、まとめ買いを分けて登録した、などで間隔0が生じて中央値が歪むのを防ぐためです。要件の「購入3回以上」は「購入した日が3日以上」と解釈します。
3. 購入日が `minEvents` 未満なら `null` を返します。
4. 隣り合う購入日の間隔（日数）を求め、直近 `maxIntervals` 個の中央値を推定周期とします（個数が偶数なら中央2値の平均）。
5. `elapsedRatio = (today - lastPurchase の日数) / medianIntervalDays`

購入履歴は直近365日分だけを取得するため（[data-model.md](data-model.md#購入履歴の取得範囲365日)）、周期がおよそ180日を超える商品は予測されません。

## リスト類似度

```kotlin
// listKey = リスト名を NameNormalizer.normalizedName と同じ方法で正規化したもの
fun buildProfiles(purchases: List<PurchaseFact>): Map<ListKey, Set<ProductId>>   // 統合先IDで集計
fun overlap(a: Set<ProductId>, b: Set<ProductId>, p: SuggestionParams): Double?  // null = 判定できない
fun relevance(target: ListKey, profiles: Map<ListKey, Set<ProductId>>, p: SuggestionParams): Map<ProductId, Double>
```

- `overlap` には **重複係数**（|A∩B| / min(|A|,|B|)）を使います。大型スーパーと小さな店のように、リストごとの商品数が大きく違っても、Jaccard 係数のように不当に低くならないためです。少ない件数で過大評価しないよう、`|A|,|B| ≥ minProfileSize` かつ `|A∩B| ≥ minIntersection` を満たさなければ `null`（関連付けない）にします。
- `relevance`: 同じ名前のリストで買ったことがある商品は1.0。それ以外は、類似度が `minOverlap` 以上のリストで買った商品に、その類似度（複数ある場合は最大値）を付けます。どれにも当たらなければ候補にしません。
- **周期の計算には全リストの履歴を使い、そのリストで提示する候補を選ぶときだけ類似度を使います。**

## 未入力時のサジェスト

`SuggestionEngine.due`:

1. 周期のグループ（なければ、名寄せの解決のまとめる先）ごとに `estimateCycle` を計算します。
2. `dueRatio ≤ ratio ≤ staleRatio` の商品に絞ります。`staleRatio` を設けるのは、「経過率の高い順」だけだと、買うのをやめた商品が常に先頭に来てしまうためです。
3. 家族の **いずれかのリスト** の未購入項目にすでにある商品（統合先で比較）を除きます。
4. `relevance(現在のリスト) > 0` の商品に絞ります。現在のリストと同じ名前の履歴も、類似するリストもない場合は **何も出さず**、「商品名を入力すると候補が出ます」とだけ表示します（場所の推定を過信しない）。
5. `ratio` の大きい順、同じなら `relevance` の大きい順に並べ、最大 `maxDue` 件にします。
6. 各候補には「約14日ごと・最後は16日前」程度の補足を表示します。

## 入力中の補完

`SuggestionEngine.complete`:

- 対象は、自分に見える項目か購入の記録がある product（統合元も含む）の `displayName` です。他のメンバーがプライベートでだけ使った商品名を出さないためです（[data-model.md](data-model.md#設計判断)）。`searchKey` の前方一致を部分一致より優先し、次に直近365日の購入回数、次に `relevance` で並べます。**周期の条件は使いません。**
- **候補の生成元は購入履歴（自分に見える項目と購入の記録）だけです。辞書は照合を助けるだけで、候補を作りません。** 辞書を使って、入力と履歴の商品を照合します（履歴が「秋刀魚」で、入力が「さんま」なら当たる）。照合には、品目名と、`exact`・`prefix` の別名を使います（`prefix` は前方一致にも使う）。表示する名前は、辞書の表示名ではなく、その商品について家族が最近使った名前にします。ただし、ほかの商品にまとめられた商品の名前（誤字など）は使わず、統合先の名前を出します。「まとめる」と「名前の訂正」は、正しい名前を決める操作でもあるためです。商品詳細入力画面の「前回: …」も同じです。非表示の商品は候補に出しません。
- 部分一致だけの候補は、直近365日に2回以上買った商品に限ります。1回だけ買った商品が、弱い一致で上位に出続けないようにするためです。
- 各候補は、一致の理由（前方一致・部分一致・辞書の別名・購入回数）を持ち、順位と表示の補足に使います。
- 候補は統合先（名寄せの解決のまとめる先）ごとに1つにまとめ、どこにもまとめられていない商品のうち家族が最近使ったものの名前を出します。選択されたらその product を使います。
- 未購入リストにすでにある商品には「追加済み」ラベルを付けます。追加はできます（追加するたびに新しい項目を作る）。
- 早すぎる再購入（下記）に当たる商品には、補足として「前回 10/18 に購入・いつもは約14日ごと」を表示します。
- 各候補には、「＋」と商品詳細入力画面で使う前回の数量・単位（その product の直近の購入）を持たせます。

## 早すぎる再購入の検知

```kotlin
data class EarlyPurchaseNotice(val lastPurchase: LocalDate, val typicalIntervalDays: Int)
fun detect(estimate: CycleEstimate?, today: LocalDate, p: SuggestionParams): EarlyPurchaseNotice?
```

- 推定が `null`（購入日が3日未満）、または `dispersion > maxDispersion`（周期が不安定）なら `null` を返します。
- `ratio < earlyRatio` のときに通知を返します。補完候補の補足と商品詳細入力画面に「前回 10/18 に購入・いつもは約14日ごと」と控えめに表示するだけで、追加の操作は妨げません。

## 備考の候補

商品詳細入力画面（新規）では、同じ product（統合先で比較）の自分に見える購入の記録から、空でない `memo` を新しい順に重複を除いて最大3件、候補のチップにします。

## AI による名寄せの候補（フェーズ6）

辞書と規則で決まらない名前を、外部の AI に判定させ、表記ゆれの候補を補います（[要件](../requirements.md) §4.2）。AI は候補を出すだけで、自動ではまとめません。

- **役割**: AI には、正規化した商品名と、備考から規則で読み取った属性（`AttributeExtractor`）を渡し、品目（日本語の標準名）・形態・容量・用途・種類・信頼度・理由を答えさせます（属性の正規化）。2つの名前が同じかは問いません。結果は名前と属性ごとにキャッシュでき、家族の中の別の名前との比較に使い回せます。
- **判定の順序**: ①手動の統合・分離 ②統合禁止（`never_merge`） ③辞書 ④キャッシュ済みの AI の判定 ⑤未判定なら AI に問い合わせる ⑥決まらなければ別の商品。④⑤は候補を出すだけなので、①〜③を覆しません。
- **候補にする条件**（端末の規則）: 2つの商品の AI の品目が同じで、属性に矛盾がなく（未指定と指定ありは一致とみなさない）、統合禁止に当たらず、信頼度がしきい値以上のとき。表記ゆれのチップ（商品詳細入力画面）と商品名の管理に「AI の候補」として理由とともに出し、選んだものだけを `mergedInto` でまとめます。「この候補を出さない」で、その組の候補を出さないようにできます。
- **問い合わせる条件**: 共有の項目で初めて購入された商品で、手動の統合・分離がなく、辞書で品目が決まらず（`ProductResolver` の判定が「自分」）、同じキーの判定がまだないとき。家族の誰かの端末が、購入の記録を書いたあとに非同期で関数を呼びます。同じキーを2台が同時に呼ばないよう、関数が `pending` で先に場所を取ります。
- **キャッシュ**: `households/{hid}/nameJudgements/{key}`（[data-model.md](data-model.md#ai-の名寄せフェーズ6)）。キーは正規化した名前と属性の組から作り、備考の全文は使いません。判定のバージョン（モデルとプロンプト）が変わったら、古い判定は使わず、次に必要になったときに問い合わせ直します。
- **失敗したとき**: 通信できない、上限に達した、応答の形が違う場合は `failed` にして候補を出しません。アプリは辞書と購入履歴だけで動き続けます。
- **費用**: 全体で月1ドル、家族ごとに月100回が上限です（[security.md](security.md#ai-の名寄せの関数)）。実装の前に、使うモデルの今の料金と、実際のプロンプトで計ったトークン数で試算し直します（当初の試算は GPT-5 nano・入力500・出力100トークン・1ドル150円で1,000回約10円）。
- **精度の確かめ方**: `dictionary/tests/cases.csv` と同じ形で、AI の判定の正例・負例の一覧を作り、本物の API で一度に流して正解率を見るスクリプトを用意します（CI では流さず、モデルやプロンプトを変えるときに使う）。規則の部分は、偽の判定を与えて JVM テストで確かめます。

## 計算の実行場所

`combine(products, purchases, openItems, currentList)` の Flow で入力をまとめ（どれも自分に見えるものだけを購読している）、`Dispatchers.Default` で再計算します。商品ごとの `CycleEstimate` は、購入データが変わったときだけ計算し直します。日付が変わったときも再計算します。
