# 追加要件: 公開範囲（家族と共有 / 自分のみ）

> **状態: 確認待ち。** 受け取った追加要件を、既存の要件・設計と突き合わせて整理したものです。[論点](#5-論点と推奨案確認してほしいこと)への回答をもらってから、[requirements.md](../requirements.md) と設計資料に反映し、この文書は削除します（反映先は [§9](#9-反映先)）。

## 1. 目的

家族で買い物リストを共有しつつ、個人的な買い物やサプライズ用の買い物を、家族から見えないようにする。普段は公開範囲を意識せずに使え、必要なときだけ変えられることを重視する。

### 利用シナリオ

| シナリオ | 操作 | 結果 |
|---|---|---|
| 通常の買い物 | 「スーパー」を作成し、牛乳・卵・食パンを追加する | 家族全員が見られ、チェックできる（今までどおり） |
| 個人的な買い物 | 共有リスト「スーパー」に商品を追加し、その商品を「自分のみ」にする | 本人の画面にだけ表示される |
| サプライズ | 「スーパー（ディナー用）」を「自分のみ」で作成し、ステーキ肉などを追加する | 商品はすべて自動で非公開になる。家族にはリスト自体が見えない |

## 2. 要件（整理後）

[論点](#5-論点と推奨案確認してほしいこと)の推奨案を採用した場合の要件です。推奨案に関わる箇所には（Qn）を付けています。

### 2.1 公開範囲の種類

- 公開範囲は「家族と共有」と「自分のみ」の2種類。リストと項目のそれぞれに設定する。
- 項目の設定は「リストに従う」（内部値 `inherit`）と「自分のみ」（`private`）の2種類。実際の公開範囲は次の表で決まる。

  | リスト | 項目の設定 | 実際の公開範囲 |
  |---|---|---|
  | 家族と共有 | リストに従う | 家族と共有 |
  | 家族と共有 | 自分のみ | 自分のみ |
  | 自分のみ | リストに従う | 自分のみ |
  | 自分のみ | 自分のみ | 自分のみ |

- 「自分のみ」のリストや項目は、作成した本人だけが見られ、操作できる。家族のオーナーも見られない。
- 他のメンバーには、非公開のリスト・項目・購入の記録・商品について、名前・数量・件数・存在のどれも分からない。

### 2.2 リスト

- 作成するとき、公開範囲を選べる。初期値は「家族と共有」。
- 作成後に公開範囲を変更できるのは、リストを作成した本人だけ（Q2）。変更の前に、影響を示す確認ダイアログを出す。
- **共有 → 自分のみ**: 自分から見えている未購入の項目は、すべて非公開になる。家族がすでに見た内容は取り消せないことを、確認ダイアログで伝える。他のメンバーが追加した未購入の項目がある場合の扱いは Q3。
- **自分のみ → 共有**: 「リストに従う」の未購入の項目だけが共有される。「自分のみ」にした項目は非公開のまま。チェック済みの項目と過去の購入の記録は共有しない（Q4）。
- 非公開のリストの名前の変更・並べ替え・削除は、本人がこれまでどおり行える。
- 一覧での並び順: 非公開のリストも、共有のリストと同じ並びの中に置く。家族が共有のリストを並べ替えると、非公開のリストとの相対的な位置がずれることがある（Q7）。

### 2.3 項目

- 追加した項目は「リストに従う」になる。追加の通常の操作（商品名 → Enter → Enter）に、公開範囲の選択は入れない。
- 共有のリストでは、未購入の項目を「リストに従う」と「自分のみ」の間で切り替えられる。切り替えられるのは、その項目を追加した本人だけ（Q5）。チェック済みの項目は切り替えられない（チェック済みの項目を編集できないのと同じ理由）。
- 非公開のリストでは、項目の公開範囲の設定を表示しない。
- 非公開の項目も、本人はチェック・Undo・編集・削除・並べ替えを今までどおり行える。
- 公開範囲の切り替えをどこで行うか（追加欄の中か、編集モードか、行のメニューか）は Q6。

### 2.4 画面

- **リスト一覧**: 共有のリストと自分の非公開のリストを、同じ一覧に表示する。非公開のリストには鍵アイコンを付ける。他のメンバーの非公開のリストは表示しない。
- **未購入件数とリストの状態**（帯の色・「まだ買うものを登録していません」など）は、見ている人が読める項目と購入の記録だけで数える。そのため、同じリストでも人によって件数が違うことがある。
- **リスト詳細**: 共有の項目と自分の非公開の項目を、並び順どおりに混ぜて表示する。自分の非公開の項目には鍵アイコンを付ける。他のメンバーの非公開の項目は表示しない。チェック済みの表示・タップでのチェックなど、ほかの振る舞いは変えない。
- **他のメンバーによるチェックの通知**: 非公開の項目は他のメンバーに見えないため、通知の対象にもならない。

### 2.5 購入履歴とサジェスト

- 共有の項目の購入の記録は、今までどおり家族で共有する。非公開の項目の購入の記録は、本人だけが読める。
- サジェスト（時期が近い商品・補完・早すぎる再購入の注意・リストの関連）は、今までどおり各端末で計算する。計算には「家族で共有している購入の記録」と「自分の非公開の購入の記録」を使う。他のメンバーの端末の計算には、自分の非公開の記録は入らない。
- 非公開の購入の記録だけから出てきた候補を、共有のリストで追加しようとした場合の扱いは Q8。
- 表記ゆれの統合（商品の統合）は、統合する商品のどちらかが非公開なら、統合の記録も非公開にする（Q9）。

### 2.6 オフライン

- 非公開のリストの作成、非公開の項目の追加・チェック・Undo・削除は、共有のものと同じくオフラインでもできる。
- リストと項目の公開範囲の変更は、オンラインのときだけ行える（Q10）。

### 2.7 データとセキュリティ

- 非公開のデータは、共有のデータと別の場所に保存し、Firestore Security Rules で本人以外の読み書きを禁止する。画面で隠すだけにはしない。
- 非公開のデータが、件数・通知・候補・商品マスタ・並び順の値などを通して、他のメンバーに漏れないようにする（[§6.3](#63-間接的な漏れの点検)）。
- 家族から外されたメンバーの非公開データは、そのメンバーも読めなくなる（共有データと同じ）。

## 5. 論点と推奨案（確認してほしいこと）

### Q1. 非公開の商品の商品マスタ（**重要**）

現在の設計では、商品を追加すると、家族共有の `products` に商品名（`displayName`）が書き込まれます。非公開の項目でもここに書くと、**商品名が家族に漏れます**。また `productId` は商品名のハッシュで決まるため、IDだけを共有の領域に書いても、ありふれた商品名なら総当たりで分かります。

- **推奨**: 非公開の項目の商品は、本人の非公開の領域の `products` に作る。共有の `products` には何も書かない。同じ名前の商品が共有にもある場合は、同じ `productId` になるので、本人の端末では自然に同じ商品として扱える。

### Q2. リストの公開範囲を変更できる人

共有のリストは誰でも名前の変更や並べ替えができます。ただ、誰でも「自分のみ」に変えられると、他の人が作ったリストを、自分のものにして家族から隠せてしまいます。

- **推奨**: リストを作成した本人だけが変更できる。作成者が家族から外された共有のリストは、変更できないまま共有で残る。

### Q3. 共有 → 自分のみ にしたとき、他のメンバーが関わる項目（**重要**）

共有のリストには、他のメンバーが追加した項目や、他のメンバーの非公開の項目が入っていることがあります。後者は、プライバシーのため、変更する本人の端末からは**存在すら分かりません**。

- 他のメンバーが追加した共有の未購入の項目:
  - **推奨**: 一緒に非公開にする（変更した人のものになる）。確認ダイアログで「花子さんが追加した3件も、家族から見えなくなります」と示す。
  - 代案: 他のメンバーが追加した未購入の項目があるときは、変更できないようにする。
- 他のメンバーの非公開の項目:
  - **推奨**: 共有 → 自分のみ の変更は、「新しい非公開のリストを作って項目を移し、元の共有のリストを論理削除する」処理として実装する。他のメンバーの非公開の項目は元のリストに残り、既存の表示ルール（論理削除されても、未購入の項目があるあいだは一覧に表示する。sync.md「リスト削除の競合」）により、その人には今までどおり見える。
  - 代案: 他のメンバーの非公開の項目は、その人からも見えなくなる（勧めない）。
- 24時間以内にチェックした項目と購入の記録は、すでに共有済みなので移さない。リストの一覧からは消える。

### Q4. 自分のみ → 共有 にしたとき、何を共有するか

- **推奨**: 「リストに従う」の**未購入の項目だけ**を共有する。チェック済みの項目と過去の購入の記録は非公開のまま残す。確認ダイアログで「未購入の5件が家族に共有されます。『自分のみ』の2件と、これまでの購入の記録は共有されません」と示す。
- 理由: 原文の「公開される情報の範囲を明確にする」を、最も狭い範囲で満たせる。購入の記録まで共有すると、サプライズの履歴が後から見えてしまう。

### Q5. 項目の公開範囲を切り替えられる人

- **推奨**: その項目を追加した本人だけ。他の人が追加した共有の項目を「自分のみ」にすると、追加した人から見えなくなってしまうため。

### Q6. 項目の公開範囲を切り替える場所

追加の通常の操作を妨げないことが条件です。

- **推奨**: 共有のリストで、数量・単位の入力（Detail）と編集モードに、「自分のみ」の切り替え（鍵アイコンのトグル）を置く。初期はオフ。商品名 → Enter → Enter の流れは変わらない。
- 代案: 追加したあと、項目の編集モードでだけ切り替える。追加と同時に非公開にできないため、一瞬だけ家族に見える（オンラインならすぐ同期される）ので勧めない。

### Q7. 並び順

並び順の値（`sortKey`）は、見えている前後の値の中間から決めます。共有と非公開のリスト・項目を同じ並びに混ぜると、他の人が並べ替えたときに、非公開のものの相対的な位置がずれることがあります。値そのものから非公開のものの存在は分かりません。

- **推奨**: ずれは許容する（非公開のものは本人が並べ直せばよい）。並び順の値が同じになったら、ID の順で並べる。

### Q8. 非公開の履歴から出た候補を、共有のリストで追加した場合

非公開で買っている商品（例: 誕生日ケーキ）が、共有のリストで「時期が近い商品」や補完候補に出ます。そのまま追加すると共有の項目になり、家族に見えます。

- **推奨**: 非公開の購入の記録だけから出た候補には鍵アイコンを付け、選ぶと数量・単位の入力で「自分のみ」がオンの状態で始める（Q6 の切り替えを使う）。
- 代案: 共有のリストでは、非公開の記録だけから出た候補を出さない。

### Q9. 商品の統合

- **推奨**: 統合する2つの商品のどちらかが非公開なら、統合の記録を本人の非公開の領域に置く。本人の端末では、共有の統合と自分の統合を合わせて解決する。両方が共有の商品なら、今までどおり共有する。

### Q10. 公開範囲の変更はオンライン限定

- **推奨**: リストと項目の公開範囲の変更は、オンラインのときだけ行える。変更は「元の場所から消して新しい場所に作る」移動になり、保留中のチェックや他の人の操作との競合を、オフラインのキューで安全に扱うのが難しいため。オフラインで操作しようとしたら、ほかのオンライン限定の操作と同じく理由を表示する。

### Q11. 他のメンバーの非公開の項目が残っている共有のリストの削除

削除する人には、他のメンバーの非公開の項目が見えません。

- **推奨**: 削除できる（見えている未購入が0件なら）。リストは論理削除なので、非公開の項目を持つメンバーには、既存の表示ルールで今までどおり表示される。

### Q12. ロードマップ上の位置づけ

- **推奨**: MVP に含め、フェーズ4（予測とサジェスト）の後に「フェーズ4.5: 公開範囲」として実装する。共有データの形を変えない方式（[§6.1](#61-データモデル)）なので、フェーズ2〜4 の実装はそのまま使える。ただし、フェーズ1で「最終形」とした domain の Repository インターフェースには、公開範囲の引数と戻り値が加わる。
- 代案: MVP の対象外にして、MVP の後に入れる。

## 6. 設計案

推奨案を採用した場合の設計の骨子です。確定後に各設計資料へ書きます。

### 6.1 データモデル

共有の領域は今のまま変えず、メンバーごとの非公開の領域を足します。

```
households/{hid}/private/{uid}                     # 本人だけが読み書きできる
households/{hid}/private/{uid}/lists/{listId}
  name, sortKey, createdBy, createdAt, status, deletedAt?, deletedBy?
households/{hid}/private/{uid}/items/{itemId}
  listId, listScope: "shared" | "private",        # 共有のリストに置いた非公開の項目か、非公開のリストの項目か
  visibility: "inherit" | "private",              # 非公開のリストの項目だけが inherit を取りうる
  productId, inputName, sortKey, quantity, unit,
  status, createdBy, createdAt, completedAt, completedBy
households/{hid}/private/{uid}/products/{productId}
  displayName, normalizedName, searchKey, createdBy, createdAt, mergedInto, mergedAt?, mergedBy?
households/{hid}/private/{uid}/purchases/{purchaseId}   # purchaseId = itemId（冪等性は共有と同じ）
  itemId, listId, listNameSnapshot, productId, inputName, quantity, unit,
  checkedAt, purchasedAt, purchasedBy, active, revokedAt, revokedBy
```

| 判断 | 理由 |
|---|---|
| 家族の下（`households/{hid}/private/{uid}`）に置く | 家族から外されたら、`isMember` の条件で本人も読めなくなる。家族をまたいだデータが残らない |
| 共有の items には公開範囲の項目を持たせない | 共有の領域にあること自体が「共有」を意味する。共有データの形が変わらないので、移行が要らない |
| 非公開の items に `visibility` を持たせる | 非公開のリストを共有に戻すときに、共有するものとしないものを分けるため（Q4） |
| 項目を移すとき itemId を変えない | `purchaseId = itemId` の冪等性と、保留チェックのキーを保つため |

### 6.2 Security Rules

- `households/{hid}/private/{uid}/**`: `isMember(hid) && me() == uid` のときだけ読み書きを許可する。
- 中身の検証（フィールドの制限・状態遷移・購入の記録との一致・サーバー時刻）は、共有の items・purchases・products と同じ規則を、非公開の領域のパスに当てはめる。
- 共有のリストに置く非公開の項目の作成は、`listId` が共有の lists に存在することを確認する。非公開のリストの項目は、本人の非公開の lists に存在することを確認する。
- リストの公開範囲の変更（Q3, Q4）は、1つのバッチ（またはトランザクション）で、移す元の削除・論理削除と、移す先の作成を行う。共有の lists の論理削除は、既存のルールで誰でもできるため、「作成者だけが変更できる」（Q2）は、移す先の作成側のルール（`createdBy == me()` と元のリストの `createdBy == me()`）で確かめる。
- 項目の移動は「元の未購入の項目の削除」と「移す先の未購入の項目の作成」になる。どちらも `status == 'open'` を要求するので、移動と同時に他の人がチェックした場合は、チェックが勝つ。
- rules-test に、他のメンバーが非公開の領域を `get`・`list`・書き込みできないこと、移動のバッチの片側だけが成立しないことを加える。

### 6.3 間接的な漏れの点検

| 経路 | 対策 |
|---|---|
| 商品マスタの商品名・ID | Q1。非公開の商品は非公開の領域にだけ作る |
| 未購入件数・リストの状態 | 見ている人が読めるデータだけで数える |
| 他のメンバーのチェックの通知 | 非公開の項目は他の人に届かないので、通知もされない |
| サジェスト・補完 | 他の人の端末には非公開のデータがないので、出ようがない |
| 購入の記録のリスト名 | 非公開の購入の記録は非公開の領域に置く |
| 並び順の値 | 値から非公開のものの存在は分からない（Q7） |
| リストの論理削除（Q3） | 元の共有のリストが削除済みになることは家族に見える。これは「家族がすでに見たリストが消えた」ことと同じで、新しい情報は漏れない |
| 招待・メンバーの削除 | 非公開のデータには関係しない |

### 6.4 購読と読み取り数

非公開の領域について、リスト・未購入の項目・リスト詳細の項目・商品・購入の記録（365日）の購読がそれぞれ加わります。いずれも本人1人分なので、件数は共有の分より少ない見込みです。リスト詳細では、共有と非公開の2つの購読をまとめて、並び順で1つの一覧にします。

### 6.5 domain

- 項目のモデルに公開範囲（共有 / 自分のみ）と、非公開のリストの項目の `inherit / private` を加える。
- 「実際の公開範囲」の判定（[§2.1](#21-公開範囲の種類) の表）、リストの公開範囲を変えるときに移す項目の選び方（Q3, Q4）、確認ダイアログの件数は、domain の純粋関数にして JVM で単体テストする。
- サジェストの入力は「共有の購入の記録 + 自分の非公開の購入の記録」、商品は「共有の products + 自分の非公開の products」、統合は両方の `mergedInto` を合わせて解決する。Q8 のために、候補ごとに「非公開の記録だけから出たか」を持たせる。

## 7. 受け入れ条件（追加）

- 共有のリストと非公開のリストを作成できる。リストの公開範囲を後から変更できる（作成した本人だけ）。
- 共有のリストに、非公開の項目を追加できる。追加の操作は「商品名 → Enter → Enter」のまま変わらない。
- 非公開のリストの項目は、すべて非公開になる。
- 本人の画面には、共有の項目と自分の非公開の項目が並び順どおりに表示され、非公開のものに鍵アイコンが付く。
- 他のメンバーの画面には、非公開のリスト・項目が表示されず、件数にも含まれない。
- 他のメンバーは、Firestore に直接アクセスしても、非公開のデータを読み書きできない（rules-test）。
- 非公開の項目を、チェック・Undo・編集・削除できる。チェックすると購入が1件だけ記録される。
- 非公開の購入の記録は、他のメンバーに読めず、他のメンバーの端末のサジェストに使われない。本人の端末のサジェストには使われる。
- 公開範囲を変えるときに確認ダイアログが出て、示した範囲を超えて共有されない（自分のみ → 共有 で、過去の購入の記録やチェック済みの項目が共有されない）。
- 既存の追加・チェック・Undo・削除・並べ替えの受け入れ条件（[requirements.md](../requirements.md) §10）が、すべて満たされたままである。

## 8. テストの追加

- domain: 実際の公開範囲の表の全パターン。公開範囲を変えるときに移す項目の選び方（他のメンバーが追加した項目、`private` の項目、チェック済みの項目）。共有と非公開を合わせた購入の記録での周期推定と、非公開の記録だけから出た候補の判定。
- rules-test: 非公開の領域への他のメンバーの読み書きの拒否。家族から外されたメンバーの拒否。移動のバッチの片側だけの書き込みの拒否。作成者以外によるリストの公開範囲の変更の拒否。
- 同時実行: 項目の「自分のみ」への切り替えと、他のメンバーのチェックを同時に行う → チェックが勝ち、切り替えは失敗する。共有 → 自分のみ の変更と、他のメンバーの項目の追加を同時に行う → 追加した項目は失われず、元のリストに残って追加した人に見える。
- Compose UI: 鍵アイコンの表示、確認ダイアログの件数、Detail の「自分のみ」の切り替えが連続入力を止めないこと。
